# 06. Reranking 발표 대본 (입문자용)

> 대상: RAG를 처음 배우는 수강생
> 방식: 비유 → 개념 → 코드 순서로 설명한다. 어려운 용어는 처음 나올 때 한 번 풀어 준다.
> 참고: 노트북에 저장된 실행 결과가 없어서, 결과 부분은 직접 실행한 화면을 보며 설명한다.

## 0. 오늘 배울 것, 한 문장으로

안녕하세요. 오늘은 **Reranking(리랭킹)** 을 배웁니다.

어려운 말처럼 들리지만 뜻은 간단합니다. **"이미 찾은 문서들의 순서를, 질문과 비교해서 다시 정하는 것"** 입니다. 이름도 Re(다시) + Ranking(순위 매기기)입니다.

오늘 수업이 끝나면 이 세 가지를 설명할 수 있게 됩니다.

1. Retriever와 Reranker는 무엇이 다른가?
2. 왜 검색을 두 번에 나눠서 하는가?
3. 코드로는 어떻게 하는가?

### 지금까지 어디까지 왔나

```text
01 Naive RAG          → 가장 기본적인 RAG를 만들었다
02 Document Processing → 문서를 잘게 잘라 DB에 저장했다
03 Query Rewriting    → 질문을 검색하기 좋게 고쳤다
04 Multi Query        → 질문을 여러 개로 늘렸다
05 Retrieval Eng.     → 검색 방식을 섞어 후보를 더 잘 찾았다
06 Reranking (오늘)   → 찾은 후보의 순서를 다시 정한다
```

---

## 1. 먼저 RAG를 아주 짧게 복습

오늘 내용은 RAG 흐름을 알아야 이해되니까 30초만 복습할게요.

```text
질문 → [문서 검색] → 찾은 문서 → [LLM에게 전달] → 답변
```

LLM은 우리 회사 문서나 최신 보고서를 모릅니다. 그래서 **질문과 관련된 문서를 먼저 찾아서 LLM에게 같이 보여 주고** 답하게 합니다. 이게 RAG입니다.

여기서 중요한 점은 이것입니다. **LLM이 받는 문서가 좋아야 답변이 좋아집니다.** 엉뚱한 문서를 받으면 엉뚱한 답이 나옵니다.

용어 두 개만 잡고 갈게요.

- **Chunk(청크):** 긴 문서를 잘게 자른 조각입니다. 이 실습에서는 페이지 단위가 아니라, 문서의 제목(heading) 구조를 따라 **최대 약 700 token 크기**로 나눴습니다. (02번에서 Docling HybridChunker로 만들었습니다.)
- **Retriever(리트리버):** 질문에 맞는 chunk를 찾아 주는 검색기입니다.

---

## 2. 왜 Reranking이 필요한가 (비유로 이해하기)

### 도서관 비유

도서관에 가서 사서에게 "추론형 데이터의 종류가 궁금해요"라고 물었다고 해 볼게요.

1. 사서가 **빠르게** 서가를 훑어서 관련 있어 보이는 책 8권을 가져옵니다.
2. 그런데 사서는 책을 하나하나 펴 보고 고른 게 아닙니다. 책을 처음 들여올 때 책마다 **"이 책은 대략 이런 내용"이라고 적어 둔 짧은 메모**를 만들어 뒀고, 질문과 그 메모를 비교해서 가져온 겁니다. 긴 내용을 짧은 메모로 줄이면 세부 내용이 빠지기 때문에, 1번으로 가져온 책이 사실은 별로 맞지 않을 수 있습니다.
   - 실제 코드에서 "메모"는 chunk(상위 제목 + 본문)를 **숫자 목록 하나(벡터)** 로 바꿔 둔 것입니다. 질문도 숫자 목록으로 바꿔서, 숫자가 비슷한 chunk를 찾습니다.
3. 그래서 이번에는 **전문가가 8권을 하나씩 펴서 내용을 꼼꼼히 읽고** "이 책이 제일 맞아요" 하고 순서를 다시 매깁니다.
4. 그중 가장 좋은 3권만 책상에 올려 둡니다.

여기서 1번의 사서가 **Retriever**, 3번의 전문가가 **Reranker** 입니다.

| | Retriever (사서) | Reranker (전문가) |
|---|---|---|
| 하는 일 | 후보를 빠르게 모은다 | 후보의 순서를 정밀하게 다시 정한다 |
| 속도 | 빠르다 | 느리다 |
| 정확도 | 대략적이다 | 꼼꼼하다 |
| 대상 | 전체 문서 | 이미 모인 후보만 |

### 왜 처음부터 전문가가 다 보지 않나요?

문서가 1만 개라면 전문가가 1만 권을 다 읽어야 해서 너무 오래 걸립니다. 그래서 **빠른 사람이 먼저 8권으로 줄이고, 꼼꼼한 사람이 그 8권만 본다**는 분업을 합니다. 이것이 오늘 수업의 가장 중요한 아이디어입니다.

```text
Query(질문)
   ↓
Retriever  : 전체 문서에서 후보 8개를 빠르게 뽑는다
   ↓
Reranker   : 후보 8개의 순서를 정밀하게 다시 정한다
   ↓
Final Top-3: 최종 3개만 LLM에게 전달
```

### 05번과의 관계

05번에서 만든 Hybrid + RRF도 "좋은 후보를 찾는 단계", 즉 Retriever 쪽입니다. 오늘은 Reranking 자체를 쉽게 보려고 **단순한 검색(Dense Retrieval)** 으로 후보를 가져옵니다. 나중에 실무에서는 05번 결과를 후보로 넣으면 됩니다.

## 3. 핵심 개념: Retriever는 어떻게, Reranker는 어떻게 비교하나

이 부분이 초보자에게 가장 헷갈립니다. 천천히 설명할게요.

### Retriever (Embedding 방식): 따로따로 읽기

질문과 문서를 **각각 따로** 숫자 목록(벡터)으로 바꾼 다음, 두 숫자가 비슷한지 비교합니다.

> 비유: 질문과 책을 서로 만나게 하지 않고, 각자 "프로필 카드"를 만들어서 카드끼리 비교하는 방식입니다.

문서는 본문 전체를 읽고 카드(벡터) 한 장으로 압축해 **미리 만들어 둘 수 있어서 빠릅니다.** 하지만 압축하면서 세부 내용이 일부 사라지고, 질문과 문서가 직접 대조된 적이 없으니 **세밀한 판단은 어렵습니다.**

### Reranker (Cross-Encoder 방식): 같이 읽기

질문과 문서를 **한 번에 같이 모델에 넣어서** "이 문서가 이 질문에 얼마나 맞는가?"를 점수로 계산합니다.

> 비유: 질문과 책을 한자리에 놓고 전문가가 직접 대조해 보는 방식입니다.

직접 비교하니 **정확합니다.** 대신 질문이 바뀔 때마다 문서마다 새로 계산해야 해서 **느립니다.**

오늘 쓰는 Reranker의 종류 이름이 **Cross-Encoder** 입니다. 이름은 어려워 보여도 "질문과 문서를 같이 읽는 모델"이라고만 기억하세요.

## 4. 실습 코드 따라가기

이제부터 노트북을 위에서 아래로 실행하면서 설명합니다. 각 셀마다 **"무엇을 하는지 → 왜 하는지 → 화면에서 볼 것"** 순서로 말씀드릴게요.

### 4-1. 환경 설정 (3번 코드 셀)

**무엇을 하나요?**
02번 시간에 만들어 둔 DB(ChromaDB)에 연결합니다. 새로 만드는 게 아니라 **이미 저장해 둔 걸 다시 열어 쓰는** 겁니다.

**알아 둘 것**

- 02번을 먼저 실행하지 않았다면 DB가 없어서 "02번을 먼저 실행하세요"라는 에러가 납니다. 일부러 넣어 둔 안내입니다.
- 임베딩 모델은 **02번과 같은 모델**을 써야 합니다. 책을 저장할 때 쓴 분류 규칙과 찾을 때 쓰는 분류 규칙이 같아야 찾을 수 있는 것과 같은 이치입니다.
- Reranker용으로 `sentence-transformers`라는 라이브러리의 `CrossEncoder`를 가져옵니다. 설치가 안 되어 있다면 `uv add sentence-transformers`를 실행합니다.

**화면에서 볼 것**
"저장된 chunk 수: ○○" 이 출력되면 DB 연결이 성공한 겁니다.

### 4-2. 후보 문서 가져오기 (5번 코드 셀)

**무엇을 하나요?**
질문 "추론형 데이터는 어떤 유형으로 구분되나요?"로 DB를 검색해서 **후보 8개**를 가져옵니다. 코드에서 `k=8`이 "8개 가져와라"라는 뜻입니다.

**왜 8개일까요? 최종은 3개인데?**
Reranker는 새 문서를 찾지 못하고 **후보 안에서 순서만 바꿉니다.** 정답 문서가 후보에 아예 없으면 아무리 잘 정렬해도 소용없습니다. 그래서 후보는 **넉넉하게** 가져옵니다.

**화면에서 볼 것**
1위부터 8위까지 chunk 번호와 페이지가 나옵니다. **이 순서를 눈여겨봐 두세요.** 잠시 후 Reranker가 이걸 바꿉니다.

### 4-3. Reranker 모델 불러오기 (7번 코드 셀)

**무엇을 하나요?**
`Qwen3-Reranker-0.6B`라는 Reranker 모델을 불러옵니다. 이름의 `0.6B`는 모델 크기가 6억 개 수준이라는 뜻으로, 큰 모델에 비하면 가벼워서 수업용으로 골랐습니다.

**알아 둘 것**
처음 실행하면 인터넷에서 모델을 내려받느라 **시간이 좀 걸립니다.** 멈춘 게 아니니 기다려 주세요.

### 4-4. 질문-문서 짝 만들기 (9번 코드 셀)

**무엇을 하나요?**
Reranker는 **(질문, 문서) 한 쌍**을 입력으로 받습니다. 그래서 후보 8개에 같은 질문을 하나씩 붙여서 쌍 8개를 만듭니다.

```text
(질문, 문서1)
(질문, 문서2)
...
(질문, 문서8)
```

**화면에서 볼 것**
"Pair 수: 8"과 첫 번째 쌍의 질문, 문서 앞부분이 출력됩니다. Reranker에 **무엇이 들어가는지** 눈으로 확인하는 단계입니다.

### 4-5. 점수 매기고 다시 정렬하기 (11번 코드 셀) ⭐ 오늘의 핵심

**무엇을 하나요?** 세 단계입니다.

1. `reranker.predict(pairs)`: 8개의 쌍 각각에 **관련성 점수**를 매깁니다. 점수가 **높을수록** 질문과 더 관련 있다는 뜻입니다.
2. `zip(...)`: 문서와 점수를 **짝지어 묶습니다.** (누가 몇 점인지 잃어버리지 않게)
3. `sorted(...)`: 점수가 높은 순서대로 **다시 줄을 세웁니다.**

**꼭 기억할 한 문장**

> Reranking은 새 문서를 찾는 것이 아니라, **기존 후보의 순서만 바꾸는 것**이다.

**화면에서 볼 것**
점수가 높은 순서대로 chunk가 나열됩니다. 이 순서가 Reranker가 새로 정한 순위입니다.

### 4-6. 순위가 정말 바뀌었나? 비교하기 (13번 코드 셀)

**무엇을 하나요?**
처음 Retriever 순위를 따로 적어 두었다가, Reranker 순위 옆에 나란히 놓고 비교합니다.

```text
Reranker | Retriever | chunk
       1 |         3 | ...      ← 원래 3등이었는데 1등으로 올라왔다!
       2 |         1 | ...
```

**복잡한 지표는 필요 없고, 이 두 가지만 보세요.**

1. Retriever의 1등이 Reranker에서도 1등인가?
2. 아래에 있던 문서가 위로 올라왔는가?

순위가 바뀌었다면, Reranker가 질문과 문서를 **같이 읽고 다시 판단했다**는 증거입니다.

> (발표 팁) 실행 결과에서 크게 올라온 문서가 있으면 그 chunk 내용을 읽어 주면서 "왜 이게 더 맞는지" 보여 주면 효과가 좋습니다.

### 4-7. 최종 3개만 고르기 (15번 코드 셀)

**무엇을 하나요?**
재정렬된 결과의 **위에서 3개만** 잘라 `final_docs`로 저장합니다.

**왜 3개만 쓰나요?**

- 관련 없는 내용이 섞이면 LLM 답변이 흐려집니다.
- LLM에 넣는 글이 길어질수록 비용과 시간이 늘어납니다.
- 그래서 **정말 좋은 문서만 골라서** 전달합니다.

이 `final_docs`가 바로 LLM에게 건네질 최종 자료입니다.

## 5. 전체 흐름 다시 한번

```text
질문
  ↓
① Retriever가 후보 8개를 빠르게 찾는다        (5번 셀)
  ↓
② (질문, 문서) 쌍 8개를 만든다                (9번 셀)
  ↓
③ Reranker가 쌍마다 점수를 매긴다             (11번 셀)
  ↓
④ 점수 높은 순으로 다시 정렬한다              (11번 셀)
  ↓
⑤ 위에서 3개만 골라 LLM에게 전달한다          (15번 셀)
```

## 6. 마무리: 세 줄 정리

- **Retriever** = 후보를 **빠르게** 찾는다. (사서)
- **Reranker** = 후보를 질문과 **같이 읽고** 순서를 다시 정한다. (전문가)
- **Reranking** = 새 문서를 찾는 게 아니라 **순서를 바꾸는 것.**

그리고 두 단계로 나누는 이유는 이렇습니다.

> Reranker는 정확하지만 느리다. 그래서 Retriever가 후보를 먼저 줄여 주고, Reranker는 줄어든 후보만 정밀하게 본다.

05번은 **좋은 후보를 찾는 단계**, 06번은 **후보의 순서를 정확히 정하는 단계**입니다. 실무에서는 두 가지를 이어서 씁니다.

## 7. 예상 질문과 답변 (초보자가 자주 묻는 것)

**Q1. Reranker가 있으면 Retriever는 필요 없나요?**
A. 필요합니다. Reranker는 느려서 문서 전체에 쓸 수 없습니다. Retriever가 먼저 후보를 줄여 줘야 합니다.

**Q2. 후보를 100개쯤 많이 가져오면 더 좋은 거 아닌가요?**
A. 정답을 놓칠 가능성은 줄지만, Reranker가 계산할 쌍이 늘어서 그만큼 느려집니다. 속도와 정확도 사이에서 균형을 잡아야 합니다. 보통 수십 개 안팎에서 시작해 조정합니다.

**Q3. 점수는 숫자가 클수록 좋은 건가요? 0~1 사이인가요?**
A. 높을수록 더 관련 있다는 뜻입니다. 다만 점수의 범위는 모델마다 다를 수 있으니, 절대값보다 **문서끼리의 상대적인 순서**를 보세요.

**Q4. 순위가 안 바뀌면 Reranking이 실패한 건가요?**
A. 아닙니다. Retriever가 이미 잘 정렬했다는 뜻일 수도 있습니다. 질문에 따라 바뀌는 정도가 다릅니다.

## 발표 전 확인 사항 (발표자용, 청중에게 말하지 않아도 됨)

- **Qwen3-Reranker와 CrossEncoder 호환성:** `Qwen3-Reranker-0.6B`는 원래 생성형 LLM 방식(yes/no 토큰 확률)으로 점수를 내는 모델이다. `CrossEncoder(...)`로 바로 불러 `predict`하면 환경·버전에 따라 점수가 기대와 다를 수 있다. 순위가 이상하면 `BAAI/bge-reranker-v2-m3` 같은 일반 Cross-Encoder 모델로 바꿔 본다. (직접 실행해 확인한 내용은 아님)
- **chunk 본문에 heading이 포함됨:** 02번에서 `page_content`는 HybridChunker의 contextualize 결과(상위 제목 + 본문)이므로 임베딩과 Reranker 입력 모두에 제목 정보가 들어간다. 임베딩 모델은 `text-embedding-3-small`(OpenAI API), 거리는 cosine이다.
- **저장된 출력 없음:** 4-5, 4-6 섹션에서 실제 순위 변화를 말하려면 노트북을 한 번 실행해 두어야 한다.
- **Q2의 "수십 개 안팎"** 은 일반적인 경험칙이며, 이 프로젝트에서 측정한 값이 아니다.
